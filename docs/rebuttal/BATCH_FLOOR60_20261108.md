# AKR Train-50：30 GB 持续显存下限的 batch 方案（2026-11-08，用户更正后）

新集群约束（用户 2026-11-08 拍板）：

* 每卡长期计算期 `torch.cuda.max_memory_allocated` 必须落在 **[30e9, 76e9] bytes**。
  底线由用户 2026-11-08 更正：≥30e9 左右即可不被平台回收（"60 GB"说法不成立）；
  上界按 76.9 GB 崩溃档避让。加载/保存阶段的瞬态跌落可容忍。
* 区间内的选择规则：**取探测曲线上区间内的最大 batch**。探测是 2 步真实前向
  （C13 为 2 步真实 LoRA optimizer step），不保存 checkpoint，不做 test 评测。
* 本文所有数字来自 `results/probe_mem_70gb_20261108.json`（1050 条测量）。
  机器可读选择结果：`results/batch_floor60_plan_20261108.json`；选择脚本
`scripts/select_batch_floor60_20261108.py`（纯数据分析，无 GPU）. Runner 输入：
`results/batch_floor60_runner_map_20261108.json`。

> 本表按 [30e9, 76e9] 重选：区间内取最大 batch（如 qwen7b dogs 8→9、bats 88→92）；
> qwen3b humbugdb 取 b=6（58.7e9，30e9 底线下合规，b=7 的 76.36e9 边缘档弃用）。
> batch-1 受限路径（GLM 19.4e9、ICL 38e9、NatureLM）用单卡多进程打包堆过 30e9。

## 2. 无法单进程入区间的格子

### 2.1 C01 qwen3b / humbugdb（已知 58.7e9）

曲线：b=6 → 58.715e9，b=7 → 76.362e9，b=8 → OOM。区间内无测量点。
Task D 单卡复测（`qwen3b_humbugdb_b7_full/lp`）：**76.3617e9**，与探测一致，
严格判定 FAIL（超上界 0.36e9）。

* 方案 A：b=7，实测 76.36e9（超上界 0.48%）。`batch_floor60_runner_map` 暂填 7；
  必须在 Task D 复测；若真实运行（generation 比 forward 多 KV cache）仍 ≤76.5e9，
  可按“差不多”接受并记录。
* 方案 B（严格合规）：b=6（58.715e9）+ 约 1.5e9 的常驻 pad tensor，
  使持续峰值约 60.2e9；pad 在整个计算期持有，记录为合规性措施。
* 决策建议：集群关机条件只针对 <60e9；若 76e9 上界允许 0.5% 工程容差，选 A；
  若上界是硬的，选 B。当前 runner map 暂填 b=7，待用户拍板。

**2026-11-08 修复后重测**（qz `job-b4ce760a-77cc-4820-a733-99dc00959897`，1×H100，

完全相同）；token/support 预算不变，仅去掉 `[1,N,N]` mask 与逐头 attention 物化。

| dataset（condition） | 输入 tokens | 修复后 b=1 峰值 | 结论 |
|---|---|---|---|
| dogs（full） | 19,668 | **25.813e9**（24.04 GiB） | ≤76e9，单进程 batch 1 可行 |
| dogs（lp:1000） | 19,668 | **25.813e9** | 可行 |
| humbugdb（full） | 24,252 | **27.965e9**（26.04 GiB） | 可行 |
| humbugdb（lp:1000） | 24,252 | **27.965e9** | 可行 |

峰值由 `torch.cuda.max_memory_allocated` 记录；基线权重 17.905e9。C04 的
watkins/bats 不在此次重测范围，但同一配置开关对它们的 ICL 前向同样生效
（峰值只会更低）。

等价性证据（`results/c04_equivalence_20261108.json`、
`results/c04_equiv_diag_20261108.json`，qz `job-9f3e34f6`/`job-77fa71d4`）：

* 50 音频 fake 输入、fp32、tiny 随机音频塔：分块 vs 整块 **max|Δ|=1.49e-8**
  （要求 ≤1e-5；`tests/test_icl_audio_attention.py`）。
* 真实 7B 权重、IEEE fp32（关闭 cuDNN TF32）：6 音频整块 vs 逐音频
  mean|Δ|=2.8e-6，max|Δ|=3.4e-3；关闭 cuDNN 后 max|Δ|=9.0e-4。同一 whole
  forward 在 cuDNN on/off 下单独就相差 max|Δ|=8.0e-3，说明 fp32 的 max 离群
  来自卷积算法选择，而非分块。
* 全部 51 音频（50 support + query）逐音频 group=1 vs group=4：
  mean|Δ|=1.7e-6，max|Δ|=1.5e-3（同为 fp32 数值噪声量级）。
* bf16：flash-varlen vs SDPA mean|Δ|=0.020；作为对照，**纯 SDPA**
  whole vs per-audio 也有 mean|Δ|=0.018（max 6.2 vs 4.8），即 bf16 差异由
  形状相关的 kernel 累积造成，非 flash 特有；单层 attention 模块级
  flash vs SDPA 为 max|Δ|=0.0156 / mean|Δ|=2.2e-4。

结论：flash 与分块使用的 `cu_seqlens` 块与 SDPA 的块对角 mask 完全一致，
token/support/prompt 预算均未改变；残余差异是 GPU kernel 数值实现差异，
与“SDPA 自身换 batch 形状”的差异同量级。

**2026-11-08 实测**（qz `job-b4ce760a-77cc-4820-a733-99dc00959897`，1×H100）：
先跑 `historical_rerun/run_historical.sh` 的 preflight/plan 阶段
（`PREFLIGHT_ONLY=1`：identity gates + register_rebuild + C16 check + core plan，
均 PASS，`C16_PREFLIGHT_RC=0`/`C16_PLAN_RC=0`）。随后在该重建 registration 上用
`FinalRunner`（qwen7b、profile 80gb、batch 1）对真实 MarmAudio 样本
`s20260914_full` 的 1 个 support + 1 个 query 做前向：

| op | batch-1 峰值（`max_memory_allocated`） |
|---|---|
| feature forward | 17.968e9（16.73 GiB） |
| support gradient（forward+backward） | **18.401e9（17.14 GiB）** |
| predict（generate） | 17.986e9（16.75 GiB） |

（`C16_PAD_BYTES=12000000000`）；C16 单进程 batch-1 本身远低于 76e9 上界，
无需多进程打包。

### 2.7 C13 LoRA（runner 语义未改）

## 4. 区间校验协议（Task D）

对每个最终配置跑 2 步真实计算（forward；C13 为 2 个 optimizer step），记录
`torch.cuda.max_memory_allocated`：

1. 单进程格子断言 `60e9 ≤ peak ≤ 76e9`。
2. 多进程格子断言各进程峰值之和（含 context 余量）在区间内。
3. 结果写 `results/batch_floor60_verify_20261108.json`，回填本文。
4. 任何 FAIL 的格子不得静默降级；按资源失败报告，或使用本文的 padding/打包备选。

### 遗留风险

* 探测是 forward，生产 runner 的 native path 是 generation（多 KV cache）。
  b=92/96 等靠近 76e9 的格子有超上界风险；Task D 必须用真实 registry 复测。
* C03 BEATs bats 的 batch 外推未经实测（只到 256）。
* C13 LoRA 真实峰值未测（探测是 micro-batch上限，不是逐条 accumulation）。
* qwen3b humbugdb b=7 超上界 0.48%，需单独判定。
* lp:1000 watkins 有低采样率文件（≤2 kHz），ICL/BEATs/feature 路径会 fail-closed；
  已有 native-bandwidth 注释机制，但 C04 lp watkins 在真实 runner 中仍可能报错。
* C16 BLOCKED，未进入任何区间校验。
* C03 的 BEATs 特征提取与 qwen 在同一个 runner 进程：若 assets 把 BEATs 放在
  `cuda`，BEATs 单独峰值 73e9 + qwen 常驻约 19e9 → 超 80GB。生产 assets 应把
  BEATs 放 CPU（本方案默认），或把 BEATs 预计算拆到专用卡；表中 BEATs batch
  只是该 pass 的独立上限。
* NatureLM 的验证是**窗口 batch**（probe/verify engine 把 B 个 10 s 窗口一次
  forward/generate）；生产 runner 的 `NatureLMBackend.predict` 仍是每窗口一次调用。
  因此 c15 作业的 max peak 来自 qwen native 阶段，NatureLM 阶段仍约 17–20e9。
  若要按瞬时下限执行，需要给 NatureLM 增加 batched predict（本轮未做）。
* 攒批的尾部/小集合会低于下限：例如 bats 的 50-support 特征矩阵在 b=92 下只有
  50 条（约 37e9），dogs/humbugdb 的 support 也需要分块。按 max peak 判定不受影响，
  但严格瞬时采样时这些阶段会跌破 60e9；需要尾部 padding 或固定 pad tensor。
* 打包的“持续”含义：静态 pad + 多进程只在**所有 component 同时存活**时保证合计
  ≥60e9；某个 component 先结束会跌到剩余进程之和。严格按瞬时采样执行时，需要
  动态 pad（按 `nvidia-smi` 的 peer 占用调整）或让同卡 component 时长对齐；
  当前模板未实现动态调整。
